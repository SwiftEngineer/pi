# Migration Hand-off: `@swiftengineer/pi-harness` → pi_agent_rust (PiJS)

**Status:** ✅ **UNBLOCKED (2026-06-30): the async-hostcall deadlock is FIXED and the fix is shipped + verified.** Root cause (see §9 #5): the rust host built its **extension worker runtime without a reactor**, so any host-async hostcall — `pi.exec`, `pi.http`, `pi.tool` — awaited from a tool's `execute()` had no timer/IO driver and deadlocked until the 60 s budget killed the tool (pure-JS timers/microtasks worked because they don't need the reactor). **Fix:** our fork [`SwiftEngineer/pi_agent_rust`](https://github.com/SwiftEngineer/pi_agent_rust) adds `.with_reactor(create_reactor())` to the extension runtime builder in `src/extensions.rs` (mirrors `src/main.rs`'s main-runtime construction). Shipped as release **`v0.1.20-reactorfix.1`** with multi-platform binaries (`pi-darwin-arm64`, `pi-darwin-amd64`, `pi-linux-amd64`, `pi-linux-arm64`, `pi-windows-amd64`; SHA256-verified). **Verified on the published `pi-linux-amd64`:** a tool that calls `pi.exec("echo",…)` from `execute()` now resolves in tens of ms (was an indefinite hang); the harness launches cleanly through it (no `Could not find export 'Container'`, all 8 pijs extensions load); `install.sh`/`update.sh` pull the fixed binary from the fork's pinned release. **This unblocks Phase 2 web tools (`pi.http`), makes Phase 3 ast-tools functional at runtime, and removes the foundational blocker on Phase 4 `task`** (it can now spawn its child `pi` via `pi.exec`). **Composition point switched to `pijs/` (2026-06-30, Phase 2→3 boundary):** `package.json` `pi.extensions` lists the ported `pijs/*.ts` (system-prompt, tool-policy, search, ast-tools, todo-write, ask, web-search, web-fetch), so the harness loads and launches under the rust `pi` binary (was failing with `Could not find export 'Container'` while it still pointed at Node `extensions/*.ts`). **Scope:** Dual-target (Node `extensions/` stays as source/fallback; `pijs/` is the Rust runtime target). **End-to-end verified (2026-06-30, against the fork binary):** Phase 2 `web_fetch` fetched+parsed a live page via `pi.http` (67 ms; raw shape `{body:string, headers:object, status:number}` — no `ok`/`text()`, seam synthesizes `ok` from status); Phase 2 `web_search` path is graceful (env has no provider keys in-sandbox → "no provider configured", confirming §9 #1); Phase 3 `ast_grep` returned 2 structural matches and `ast_edit` rewrote a file on disk (raw `pi.exec` shape `{code:number, killed:boolean, stdout:string, stderr:string}`); Phase 4 foundation (child `pi` sub-agent spawn via `pi.exec` from `execute()`) confirmed working. The three §9 #5 seam-hardening items (M1/M2/L1) are **applied** using the confirmed shapes; `pijs` typecheck is clean. **Remaining:** port Phase 4 `task` itself and re-test §9 #9 (non-blocking continuation); optionally open an upstream PR for the reactor fix. **⚠ Driving gotcha (rust `pi`):** `--mode json` and redirecting stdout to a regular file (`> out`) both HANG the process; drive verification in default text mode with stdout through a **pipe** (`| cat`/`| head`) and have the tool echo its result as the final message.

This document is the authoritative, self-contained plan. It assumes the reader has the repo and the [pi_agent_rust](https://github.com/Dicklesworthstone/pi_agent_rust) reference, but nothing else.

## 1. Context and headline finding

This repo is a Pi *extension package*, not a terminal harness. Every file is a plugin loaded by a host (`@earendil-works/pi-*` on Node). `pi_agent_rust` is a from-scratch Rust port of that host that **ships a QuickJS-based "PiJS" runtime designed to load legacy JS/TS Pi extensions** (per the upstream README it conformance-tests against a frozen pi-mono extension corpus; the ~92% figure is from upstream docs and is **unverified here**). That makes a real port possible — but it is **not a batch translation**. Files split into tiers by which host surfaces they touch.

**Three structural realities drive the whole plan:**

1. The PiJS runtime calls `execute(toolCallId, input, undefined, undefined, ctx)` — `signal`/`onUpdate` are always `undefined`. Any abort/timer machinery built on those args is inert.
2. The runtime validates `parameters` as JSON Schema (`type`/`properties`/`required` only) and reads only `{ name, description, label?, parameters, execute }` from a tool spec — `promptSnippet`/`promptGuidelines`/`executionMode` are silently dropped.
3. npm dependencies do not function in the QuickJS sandbox (`glob` is a shallow stub; `ignore`, `jiti`, `@ast-grep/cli`'s bin path are not available). Pure-logic deps must be reimplemented; binary deps must be resolved to a real on-PATH executable.

## 3. The confirmed PiJS target surface

> **Provenance note.** §3 below is grounded in two parallel research passes over (a) the canonical pi-mono example extensions + `extensions.md`, and (b) `pi_agent_rust`'s `extensions_js.rs` (30k lines), `extensions.rs`, WIT, and capability docs. These external artifacts are not in this repo and could not be re-checked locally. Treat the entries marked **[research]** as well-sourced but unverified-locally; only the `tool_call`→`{block,reason}` and tool-spec `{name,description,label?,parameters,execute}` contracts are independently confirmed by the Phase-0 slice (`pijs/ADAPTER.md`). The remaining entries should be re-confirmed against a real binary (§9).

**Registration** (identical method names to the Node host) **[research]**:
```js

pi.on(eventName, async (event, ctx) => ({ /* optional decision */ }));
pi.registerCommand(name, { description, handler: async (args, ctx) => {} });
pi.registerShortcut(key, { description, handler: async (ctx) => {} });
pi.registerMessageRenderer(customType, renderer);
pi.sendMessage(message, options);
pi.exec(cmd, args, options);   // capability: exec

pi.events(op, args); pi.events.on/emit;
```

> **GAP — `context.ts` needs more than this.** Beyond the imports it shares with the Node host, `context.ts` calls `pi.getActiveTools()` / `pi.getAllTools()` and `ctx.getContextUsage()` / `ctx.getSystemPromptOptions()` / `ctx.getSystemPrompt()` / `ctx.sessionManager.getBranch()`. **None of these are confirmed to exist on the PiJS `pi`/`ctx` surface** (they are not in the registration list above). See §9 #5b — resolving this is what makes `context.ts` a true rewrite, not an adapter.

**`execute` contract:** host invokes `execute(toolCallId, input, undefined, undefined, ctx)`. Returns `{ content: [{type:"text",text}], details: {...}, terminate?: true }`.

**Events** (29 total, all `snake_case`) **[research]**: `startup`, `input`, `before_agent_start`, `context`, `agent_start`, `agent_end`, `turn_start`, `turn_end`, `message_start`, `message_update`, `message_end`, `tool_execution_start/update/end`, `tool_call`, `tool_result`, `session_start`, `session_before_switch/fork/compact/tree`, `session_switch/fork/compact/tree`, `resources_discover`, `model_select`, `user_bash`, `session_shutdown`. Key contracts:
- `tool_call` receives `{ toolName, toolCallId, input }`; return `{ block: true, reason }` to abort (early-stop semantics; thrown errors propagate).
- `before_agent_start` receives `{ systemPrompt, prompt, systemPromptOptions }` (payload shape is **[research]**; the in-repo `system-prompt.ts` only ever returns `{ systemPrompt }`, so only the return contract is locally exercised); return `{ systemPrompt, message? }` to inject/replace the prompt. **This is the system-prompt injection event** (per the JS dispatcher), not `session_start`.
- `session_before_*` return `{ cancel: true }`.

> **Two caveats on this list (reconcile against a binary):**
> 1. **In-repo events outside the 29.** `tui-powerline.ts` subscribes to `thinking_level_select`, which is **not** in the list above. Under PiJS the effort/thinking-level segment would silently fall back to its default. Mark this extension's effort segment as degraded until confirmed.
> 2. **Host events ≠ child-process JSON events.** `task/index.ts` does **not** use `pi.on` for streaming — it parses newline-delimited JSON from a **child `pi --mode json` process's stdout** (`parseEvent`). Those line types (`turn_start`, `message_start/update/end`, `tool_execution_start/end`, `agent_end`, **`auto_retry_start`**) are a *different* channel and are not governed by the host's 29-event set. `auto_retry_start` in particular is **not** a host event — it only appears in the child JSON stream. Don't conflate the two.

**Capability → hostcall mapping [research]:** `read` (read/grep/find/ls tools), `write`, `exec` (bash/`pi.exec`), `http` (`pi.http`), `session`, `ui`, `events`, `tool` (other tools), `env` (`pi.env.get`), `log`.

**Default policy (Standard/Prompt) [research]:** allowed = `read, write, http, events, session`; **denied = `exec, env`**. Configurable per-extension via a capability manifest; `Safe` profile is stricter (`exec, env` denied, only read/write allowed); `Permissive` allows all.

**Supported `node:` builtins in the sandbox:** `path`, `fs`, `fs/promises`, `crypto`, `buffer`, `child_process` (capability-gated), `http`/`https`, `events`, `os`, `url`, `process`, `util`, `stream` — all shimmed (see `docs/ext-compat.md`).

## 5. Cross-cutting concerns (must be decided once, affect many files)

### 5.1 The `env` capability problem
`exec` and **`env` are denied by default.** Several extensions read secrets/config from `process.env`:
- `web-search.ts`: `BRAVE_API_KEY`, `TAVILY_API_KEY`, `KAGI_API_KEY`
- `web-fetch.ts`: (none directly, but inherits timeout config pattern)
- `tui-powerline.ts`: `HOME`/`USERPROFILE`
- `task/index.ts`: `SWIFT_PI_COMMAND`, `PI_TASK_*` tuning vars
- `ast-tools.ts`: `process.platform`

**Mitigation (pick one, applies to all):** grant the `env` capability in each extension's manifest, OR confirm whether the shimmed `process.env` is subject to secret-filtering rather than a hard capability gate. **Open until a binary is available** — see §9. This is the single most important cross-cutting unknown.

> **Exhaustive `env` reader inventory** (verified by repo search): `web-search.ts` (`BRAVE_API_KEY`/`TAVILY_API_KEY`/`KAGI_API_KEY`), `tui-powerline.ts` (`HOME`/`USERPROFILE`), `task/index.ts` (`SWIFT_PI_COMMAND`, `PI_TASK_*`), `ast-tools.ts` (`process.platform`), `animated-pi-header.ts` (`HOME`/`USERPROFILE` via `formatDirectory`), `subagent-view/index.ts` (`PI_SUBAGENT_DEBUG`, `PI_ASCII`, `LC_ALL`, `LC_CTYPE`, `LANG`). `web-fetch.ts` reads none directly. The capability question applies to all of these identically.

### 5.2 Network: global `fetch` vs `pi.http()`
`web-search`/`web-fetch` use the global `fetch`, `URL`, `AbortController`. The Bun-compat layer stubs network (`Bun.connect/listen` = no network). Whether the global `fetch` is wired to real networking is **unconfirmed**. Safe path: rewrite both to `pi.http()` (capability `http`, confirmed). This makes them **moderate**, not easy.

### 5.3 Timers / event loop — and the `task` background-execution blocker
`setInterval`/`setTimeout`/`AbortController`/`performance.now()`/`Promise.withResolvers` are used by `task/index.ts`, `web-fetch.ts`, `animated-pi-header.ts`, `subagent-view/index.ts`. QuickJS has no Node event loop; whether the host bridges timers is **unconfirmed**. Affects: the animated header's render loop (likely broken), task's kill/force-resolve timers (may degrade to host-budget cancellation), web-fetch's request timeout (use `pi.http()` timeout options instead). **Open** — see §9.

> **⚠ P0 architectural risk — non-blocking background execution for `task`.** The `task` tool's core contract is: `execute()` **returns immediately** while `runBackgroundBatch(...)` keeps running, and later calls `pi.sendMessage({customType:"subagent-results",…}, {triggerTurn:true, deliverAs:"followUp"})`. **Update (reactor fix, 2026-06-30):** the old "with no event loop there is no scheduler" framing no longer holds — the fork binary (`v0.1.20-reactorfix.1`) gives the extension runtime a reactor, so async hostcalls and timers run from `execute()`. The open question narrows to: can `execute()` **return** to the host while a continuation keeps running on that reactor and later delivers via `sendMessage`? (A `pi.exec` streaming via `onChunk` still blocks `execute()` until the child exits, so a non-blocking design must hand work to a background continuation rather than await it inline.) If background continuations are unsupported, fall back to a **blocking** `task` (results inline on completion). Gated as §9 #9; gates Phase 4.

### 5.4 Shared helpers → `pijs/_shared/`
The slice already duplicates glob/gitignore/utf8 logic. Extract shared modules to avoid divergence:
- `pijs/_shared/glob.ts` — `globToRegex`, `matchGlob`, `walkFiles`, `expandInput`
- `pijs/_shared/ignore.ts` — `loadIgnore`, `makeIgnore`
- `pijs/_shared/text.ts` — `utf8ByteLength`, `utf8Head`, `truncateLine`, `tailBytes` (from `registry.ts`), `BoundedText` (from `task/index.ts`), **and `visibleWidth`/`truncateToWidth`** (ANSI-aware wcwidth + truncation, currently imported from pi-tui by *both* `tui-powerline.ts` and `subagent-view/strip.ts`; not stubbed in PiJS, so must be reimplemented here before either can port).
- `pijs/_shared/format.ts` — `formatBytes`, `formatNumber`, `formatTokens`

Refactor the slice to import these once the second consumer lands.

### 5.5 Extension discovery/loading — and cross-extension module sharing
The Node host uses `package.json` `pi.extensions`. pi_agent_rust loads via `extension.json` manifests + discovery (`--extension <path>` CLI, or `~/.pi/agent/extensions/`). Each `pijs/*.ts` likely needs a sibling `extension.json` declaring `extension_id`, `entry_path`, `capabilities`. **Confirm the exact manifest schema against the binary** (see §9).

> **Two coupled unknowns:**
> 1. **`.ts`-suffixed relative imports.** Every `subagent-view/*` file imports siblings with explicit `.ts` suffixes (e.g. `import { maxTop } from "./scrollback.ts"`), and `task/index.ts` imports `"../subagent-view/registry.ts"`. Whether the QuickJS module resolver handles `.ts` extensions is unconfirmed — confirm against the binary, or plan to strip suffixes / pre-resolve at load.
> 2. **Cross-extension singleton sharing.** `task` and `subagent-view` are **two separate `pi.extensions` entries** (see `package.json`) that share one in-memory `subagentRegistry` via the `globalThis.__piSubagentRegistry__` singleton — *because* they are separate modules evaluated independently. Under PiJS, whether two `extension.json` entries share one QuickJS global (so `globalThis` works as the rendezvous) or run in isolated runtimes is unconfirmed. If isolated, the registry cannot be shared and the two extensions must be merged into one entry. This couples to §9 #7 and gates Phase 4.

### 5.6 Schema keyword policy
`parameters` is validated as JSON Schema reading **only** `type`/`properties`/`required`. All other keywords — `enum`, `anyOf`, `oneOf`, `description`, array `items`, nested `properties` — are **not validated** by the host; they survive as documentation/type-hints for the model. The existing `pijs/search.ts` slice already relies on this (its `paths` field uses unvalidated `oneOf`). **Port policy:** keep descriptive keywords for the model's benefit, but perform any real validation (e.g. enum membership, union shapes) **inside `execute`**. `todo-write.ts` (`op` enum) and `web-search.ts` (`recency` enum) must validate their enum fields in code, not rely on schema.

### Phase 3 — ast-tools (PORTED 2026-06-30 — ✅ VERIFIED functional on the fork binary, see §9 #5)
> **Update (verified, 2026-06-30):** the §9 #5 deadlock is FIXED in the fork release `v0.1.20-reactorfix.1` (now the installed `pi`), and Phase 3 is verified end-to-end — `ast_grep` returned 2 matches and `ast_edit` rewrote a file on disk (details in the exit-criteria below). The three `_shared/exec.ts` seam-hardening items (M1/M2/L1) are applied using the confirmed `pi.exec` shape `{code,killed,stdout,stderr}`; `pijs` typecheck is clean.

**Work done:** ported `ast-tools.ts` → `pijs/ast-tools.ts`; added `pijs/_shared/exec.ts` (the single defensive seam over `pi.exec`, normalizing to `{ code, stdout, stderr }`); registered `./pijs/ast-tools.ts` in `package.json` `pi.extensions` (after `search.ts`).
- **`import.meta.url` IS supported** (probed live: returns `file:///…/pijs/ast-tools.ts`); **`import.meta.dirname` is `undefined`**. So the original `import.meta.url` anchor was KEPT (not dropped): the resolver strips `file://`, walks up from the file's dir, and probes package-local binary candidates with `fs.existsSync` (reads work in the sandbox). `pi`/`ctx` expose **no** package/extension-root field (probed: `pi` has no `root`/`dir`/`packageRoot`; `pi.process.cwd` is a string, calling it throws "not a function"), and `ctx.cwd` is the user's working dir (possibly a different repo), so it is **not** a reliable anchor for the package's own `node_modules` — confirming `import.meta.url` is the correct anchor.
- **`sg` resolution (the trap):** a bare `sg` on PATH is `/usr/bin/sg` = shadow's set-group tool, NOT ast-grep (its `--version` prints `Usage: sg group …`); `ast-grep` is not on PATH at all. The resolver prefers the package-local dependency `<pkgRoot>/node_modules/@ast-grep/cli/{ast-grep,sg}` (+ `.bin/{ast-grep,sg}` symlinks, provided by `@ast-grep/cli@0.44.0`); only if no package-local binary exists does it fall back to PATH names `ast-grep`/`sg`, accepting one **only** if `<name> --version` output contains "ast-grep" (rejecting shadow's `sg`). Else it returns a clear actionable error rather than running the wrong binary.
- **`pi.exec` hangs at load (§9 #5)** — all binary resolution (the `fs` probe AND the optional `--version` PATH probe) runs **lazily inside `execute()` on first call and is cached** in a module-level var; nothing touches `pi.exec`/resolution at module load or activate(). Verified: the package loads with no hang.

### Phase 4 — task + registry  ✅ IMPLEMENTED (non-blocking, full Node parity via host pump) — reviewed+tested 2026-06-30
> **§9 #9 RESOLVED (updated) — non-blocking IS viable via a host-side pump; `task` now has full Node parity.** The earlier conclusion ("non-blocking is not viable, so `task` is blocking") held only for the *stock* extension runtime, which has no independent event loop: background JS advances **only** while a host→extension frame is on the stack, so an un-awaited continuation froze the instant `execute()` returned. **The fix is host-side, in our fork:** the host already carried a built-but-unused `pump_once()` driver; fork commit `89b112c4` (branch `feat/pump-extensions`, shipped as fork release **`v0.1.20-reactorfix.2`**) wires it to a self-clocking `PiMsg::PumpExtensions` timer (adaptive 50 ms active / 400 ms idle) that advances background extension JS **between** host frames. It is gated off while a turn is streaming, an extension tool is executing, or a compaction is in flight (single-threaded worker contention), guarded against overlapping pumps by `pump_in_flight` (with an RAII reset so a panicking pump can't wedge it off), and disabled under `PI_TEST_MODE`. With the pump running, an un-awaited continuation keeps making progress and can call `pi.sendMessage` autonomously while the session is idle — exactly what `task` needs. (§9 #6 stays CONFIRMED: `pi.sendMessage(msg, {triggerTurn:true, deliverAs:"followUp"})` is honored; the pump is what lets a background frame *reach* that call.)
>
> **`task` is therefore implemented NON-BLOCKING with all five Node properties:** (1) `execute()` validates, seeds the registry, fires an **un-awaited** `orchestrate()` and returns `"Started N background sub-agents"` immediately; (2) children run **detached and in parallel** — each is launched as `setsid sh -c '…' </dev/null >/dev/null 2>&1 &` so the launching `pi.exec` returns at once, and the wave loop honors `MAX_CONCURRENCY=4`; (3) the sub-agent **strip updates live** off the `globalThis` `subagentRegistry` as each child streams; (4) combined results arrive **autonomously** as a `subagent-results` follow-up turn via `pi.sendMessage(…, {triggerTurn:true, deliverAs:"followUp"})`; (5) temp dirs are cleaned up. Long-running children are supported because they are **detached, not awaited** — each is `timeout`-bounded (`PI_TASK_CHILD_TIMEOUT_MS`, default 30 min), so the whole batch is *not* subject to the ~60 s per-`execute()` tool budget. The orchestration polls each child's out-file via one batched boundary-framed `pi.exec` read per tick, drains new complete lines into the registry exactly-once (offset-tracked), and on child-done does a settle-time re-read to recover any final `message_end` flushed between the poll's `cat` and its done-check. **Session-shutdown parity:** each child records its `setsid` group-leader pid to a `pid-i` file; a `session_shutdown` handler best-effort `kill -TERM -<pid>`s the whole group (guarded by a `/proc/<pid>/cmdline` batch-token match so a reused/foreign pid is spared), then removes the batch dir. Exactly-once delivery is enforced by a `delivered` flag set before the send.
>
> **Runtime facts (still true, and why the design is shaped this way):** the per-`execute()`/per-pump host tool budget is ≈ **10 s** (`EXTENSION_QUERY_BUDGET_MS`), so long children **must** be detached rather than awaited inline; the host **serializes** JS-level `pi.exec` calls, so parallelism comes from the shell-detached children (not concurrent awaits); `pi.exec`'s `{timeout}` option is honored in ms; the spawned child inherits a working provider via config default (no `--provider` needed); the host exec-mediation **denies `rm -rf`** (cleanup uses `rm -f <files>; rmdir <dir>`) and denies `kill -9 <pid>`/`killall` (shutdown uses `kill -TERM -<pid>`). **Ported files:** `pijs/task/index.ts`, `pijs/subagent-view/registry.ts`, `pijs/subagent-view/transcript.ts`, `pijs/_shared/text.ts` (`BoundedText`/`countNewlines`/`utf8Head`/`tailBytes`/`clipToLineLimit`) + the `_shared/exec.ts` seam. **Tunables:** `PI_TASK_POLL_INTERVAL_MS`, `PI_TASK_ORCH_BUDGET_MS`, `PI_TASK_CHILD_TIMEOUT_MS`. **Verified (PTY, real fork binary + independent review + independent test):** all 5 properties hold; injection-safe across 7 metacharacter classes (canonical `shQuote` `'…'\''…'` + trailing `--`, zero artifacts); failing / oversized (6 > cap 4) / edge batches all settle and deliver; no leaked temp dirs, hangs, or double-delivery; `tsc` clean; `node pijs/smoke.mjs` 30/30. **Iteration fixes applied after review:** settle-time tail re-read (event-loss race), `session_shutdown` group-kill parity, exactly-once `delivered` guard, `reapStaleGhosts` docstring. **Remaining known edge (deferred, bounded):** a sub-agent's *own* subprocess that isolates into a separate process group survives the shutdown group-kill until the child `timeout` fires — kept as-is to preserve the long-running property (the group-kill handles the primary sub-agent process; `timeout` is the backstop).
>
> ⚠ **PiJS runtime gotchas discovered here (apply to all later phases):** (a) the TS loader **corrupts on a typed private-class-field declaration** (`#f: T = v` and `#f = v as T` both throw `undefined private field` at load) — use `private`-modifier fields declared type-only + initialized in the constructor; (b) the module loader **rejects absolute module specifiers and `../` paths that escape the extension's virtual root** — cross-module imports must stay within the `pijs/` tree via relative paths; (c) driving a tool for verification: default **text mode + stdout through a pipe** (NOT `--mode json`, NOT `> file` — both hang), with the tool echoing its result as the final message.

1. **Parity harness (`pijs/smoke.mjs`)** — load each `pijs/*.ts` through a fake `pi` (mirroring the existing `scripts/smoke.mjs` technique) and assert output byte-for-byte against the Node `extensions/` over identical inputs. This works *without* a binary and is the main safety net during porting.

3. **Behavioral diff** — for `search`, run the Node and PiJS tools over the same repo+pattern and diff; for `task`, run the same assignment under both and compare the delivered result.
