## Context

v1 (`background-subagents`) spawns each subagent as `pi --mode json -p --no-session "<assignment>"` with stdin ignored: a fire-and-forget process whose context is destroyed at exit. The parent captures the full message log for replay, but there is no channel to continue the conversation — the implement→review→fix loop either redispatches from scratch or pastes lossy summaries.

This change's premise: neither daemons nor a new IPC protocol are needed, because Pi already provides the missing primitives:

| Primitive | Verified behavior (source-grounded) |
|---|---|
| `--session-id <id>` | `main.js` `createSessionManager`: looks up the exact id among project sessions in the effective session dir; **opens the existing session if found, else creates a new session with that exact id**. `assertValidSessionId` requires ids to start and end with an alphanumeric (interior `._-` allowed) — the v1 record-id shape (`sa-<base36>-<n>`) qualifies. Cannot be combined with `--session`/`--continue`/`--resume` (validated; we never need them). |
| Orphaned-turn repair | `pi-ai` `transformMessages` second pass: inserts synthetic `isError` tool results ("No result provided") for tool calls that never received results, and skips assistant messages with `stopReason` `error`/`aborted` entirely. A session killed mid-tool-execution therefore resumes as a provider-valid history. |
| Lazy session-file creation | `SessionManager._persist` creates the session file only once an entry containing an **assistant** message exists (before that, entries are buffered in memory). A child killed before its first assistant response leaves **no session file at all** — the reason D8's existence guard is mandatory, not optional. |
| Resume stream hygiene | A resumed `--mode json -p` child streams only the new engagement's events (print mode subscribes to live session events; no history replay on stdout), so parent-side capture never duplicates prior turns. |

Session messages persist at `message_end` (`agent-session.js` `_handleAgentEvent` → `appendMessage`), so a SIGTERM mid-tool-execution leaves the session with a dangling tool call — repaired by the table above on the next request. No extension-side repair logic is required or permitted.

Session lookup (`SessionManager.list(cwd, sessionDir)`) is scoped by cwd; children run in the parent's cwd, so dispatch and resume agree within a parent process. Across a pi restart the cwd must still match, and the session file may or may not exist (lazy creation, OS tmp policy) — both failure modes must be explicit errors, not silent fresh sessions (D8). Session files are named `<timestamp>_<sessionId>.jsonl`, so existence is checked by directory scan for the `*_<id>.jsonl` suffix, not by direct path.

## Goals / Non-Goals

**Goals:**
- A finished, failed, aborted, or lost agent can be re-engaged by the parent with full prior context, under its original identity — with any context gap surfaced as an explicit error, never silently.
- A running agent can be interrupted and redirected by the parent in one atomic operation.
- Per-turn delivery and persistence: an agent's Nth engagement delivers its Nth result.
- No daemons, no IPC protocol, no parked processes, no message queues. The only synchronization required is a sequential execution mode and a synchronous engagement claim enforcing the single-writer invariant (D9).

**Non-Goals:**
- **True mid-run steering without kill (v2b).** Injecting a message at the next tool boundary of a live process requires RPC-mode children and a stdin command channel. Kill-and-resume covers the correction use case; the latency difference is one process spawn.
- **Queuing messages to running agents.** A send to an in-flight agent without `interrupt` is rejected, not queued. The rejection path itself must be race-free — that is D9's synchronous claim, not a queue. We are not building delivery-queue state.
- **Session retention/pruning policy.** Session files live under the OS temp dir and are not pruned by the extension (OS tmp policy applies). Reclaim-induced loss degrades re-engagability, not correctness: D8 turns a missing file into an explicit send failure. A retention policy is future work if tmp growth ever matters.
- **Cross-cwd re-engagement.** Session lookup is cwd-scoped; an agent is re-engaged from the project it was dispatched in. A lookup miss fails the send explicitly (D8).
- **Nested delegation.** Stays removed (v1 D10); `subagents_send` is registered under the same `SWIFT_PI_SUBAGENT` gate.
- **Operator-facing send UI.** The parent LLM is the actor; operator hotkeys remain select/replay/abort.

## Decisions

**D1 — Re-engagement is a fresh one-shot child on a durable session; no daemons.** Both re-engage and interrupt-and-resume spawn a new `pi --mode json -p` child, identical in shape to a v1 dispatch except for spawn flags (D2) and the prompt being the feedback/correction message. The v1 child-runner core (`runChild`), stream parsing, status derivation, and delivery are reused unchanged. *Rationale:* every hard part — SIGTERM escalation, stream capture, guarded callbacks, follow-up delivery — already shipped and is verified; the only new mechanics are spawn flags and re-attaching a child to an existing record. Process exit remains the liveness boundary, so no idle management exists to get wrong.

**D2 — Deterministic session identity: `--session-id <record id>` in a private `--session-dir`.** Spawn args become:

```
pi --mode json -p --session-dir <tmp>/swift-pi-subagent-sessions \
   --session-id <record id> --append-system-prompt <role prompt file> "<prompt>"
```

The dir is shared across parent sessions (not per-session) so re-engagement survives a pi restart; the OS owns cleanup. The same invocation creates the session on first dispatch and resumes it on every later engagement — dispatch and resume are one code path, not two. The stderr warning classification is split by engagement kind: on **first dispatch** ("creating a new session with that id") it is expected diagnostic noise; on a **resume engagement** the same warning means the durable session was missing and is a hard failure signal (D8). *Rationale:* the parent chooses the id up front, so no path bookkeeping; and `--session-dir` keeps subagent sessions invisible to the human's resume picker.

**D3 — `subagents_send` semantics: reject-don't-queue, interrupt is atomic.**

```
subagents_send({ id, message, interrupt? })
  target in flight,  interrupt true  → SIGTERM (v1 escalation path) → await close
                                        → spawn resume child, prompt = message
                                        (intermediate aborted delivery suppressed, D11)
  target in flight,  interrupt unset → tool error: "agent still running; abort it
                                        (interrupt: true) or wait for its result"
  target terminal (done/failed/aborted/lost) → verify durable session exists (D8)
                                        → spawn resume child, prompt = message
  unknown id                         → tool error listing known agent ids
```

The in-flight kill path reuses the v1 abort mechanics exactly (SIGTERM, 5 s SIGKILL escalation); the record transitions through the same `aborted` status before the resume spawn flips it back to waiting/thinking. TUI mode returns a dispatch ack immediately; non-TUI blocking mode awaits the resume child and returns its result inline (mirrors v1 D2's fallback split). All engagement paths claim the record synchronously and serialize per D9, and re-engagement model behavior follows D10.

**D4 — Records are turn-shaped; finalize and delivery happen per turn.** One registry record per agent for its whole life: `messages` accumulates across engagements, usage accumulates (already additive), and the status machine runs once per engagement (waiting → thinking/working → done/failed/aborted). v1's `finalized` once-flag becomes per-turn: each engagement's completion appends a **new completion entry** (full message log, v1 precedent — deltas are a future optimization) and delivers a `subagent_result` followUp. **Every engagement start resets the engagement-scoped fields** — `finalized → false`, `status → waiting`, `stderr → ""`, `abortRequested → false`, `stopReason/errorMessage → undefined` — and the restore path must un-terminalize restored-lost records the same way; without this reset a resumed engagement never finalizes, never persists, and never delivers. Restore folds completion entries **latest-entry-wins**: each entry embeds the full cumulative message log and cumulative usage, so the newest entry *is* the record's current state; earlier entries remain in the session for delivery-history display. Restore-on-session-start is otherwise unchanged in mechanism: a dispatch entry with no completion entry restores as aborted ("lost") — re-engagable *pending* the D8 existence check, because its session file may have survived in the private dir (or may never have been created).

**D5 — Delivered results carry the agent id in the LLM-visible header.** `resultHeaderText` becomes `[subagent <type> <id> — <status>] <task>`. The dispatch ack already includes ids; the delivered header is the second (and repeated) exposure the parent needs to address an agent later. Without this the tool is unreachable from real conversations.

**D6 — Role prompt is re-staged per engagement.** v1 writes the role prompt to a temp file per spawn and deletes it at close. Resume spawns re-stage it from `AGENT_PROMPTS[type]` identically, so every engagement of an agent carries the same system-prompt framing. No persisted copy of the role prompt is needed.

**D7 — The review loop is a prompt-guidance pattern, not machinery.** The system prompt gains one guidance block: results carry agent ids; use `subagents_send` to re-engage (e.g. route reviewer feedback to the implementer) or `interrupt: true` to redirect a runaway; cap fix iterations (e.g. 2–3) before reporting residual issues back instead of ping-ponging. Note that sends serialize within a turn (D9). No orchestration state, no loop detection in code for v2a.

**D8 — Re-engagement requires a durable session, verified before spawn.** `--session-id` is create-or-open, and pi creates the session file only at the first assistant message (see Context). Three paths therefore produce a *silent blank session* if unchecked: a child killed before its first assistant response (no file ever created), OS tmp reclaim, and a cross-cwd lookup miss. The send tool MUST verify the session file exists before spawning any resume child — scan the private dir for `*_<record id>.jsonl` (a scan *error* is reported as "cannot verify", distinct from a miss). On miss, fail the send with "durable session missing — cannot re-engage". Belt-and-braces: on a resume engagement, the child's stderr "creating a new session with that id" warning is treated as a hard failure signal (it only fires when the file was missing) — and that failure is *sticky*: the `resumeSessionMissing` flag rides on the failed engagement's completion entry, is restored with the record, and refuses all further sends on that record even though the now-created blank file passes the existence scan (the scan alone would silently "self-heal" a poisoned record). Restored-lost records are marked re-engagable *pending* this check, never unconditionally. *Rationale:* the change's central promise is "continues with full prior context"; an unverifiable promise must fail loudly, and stay failed.

**D9 — The single-writer invariant is enforced, not asserted: three layers.** Two processes appending to one session JSONL corrupts it, and pi runs tool calls in parallel by default. (a) **Sequential execution mode:** `subagents_send` declares `executionMode: "sequential"` — the agent loop runs any tool batch containing a sequential tool fully sequentially (verified in `agent-loop.js` `executeToolCalls`), so parallel sends on the same record cannot interleave. Dispatch stays parallel (each task owns a fresh record). (b) **Synchronous claim + in-flight check:** the send handler claims the record *before* its first await — the engagement's run handle (`record.run`) is set synchronously and the prompt is passed to the child spawner as a captured argument, not re-read from the mutable record after the staging awaits — and the in-flight check consults `record.child || record.run`, so a second send that lands in the pre-spawn window (claimed but not yet spawned) is rejected instead of silently dropping its message and clobbering the pending prompt. (c) **Cross-restart pid probe:** the dispatch entry records the first child's pid and every resume spawn appends a small engagement entry carrying the new pid; restore probes the *latest* pid across all entry kinds, so a parent crash mid-resume still leaves the orphan visible. A send on any restored record whose recorded pid is still alive (`process.kill(pid, 0)`) refuses (EPERM counts as alive — fails safe; a false positive from pid reuse costs only a spurious refusal). The debug spawn assertion (no record ever has two live children) remains as a regression tripwire, not as the mechanism. A claimed-but-unspawned engagement is never orphaned by shutdown or an abort that lands in the staging window: the child spawner re-checks `abortRequested` after its own awaits and refuses to spawn a child nobody is waiting to kill.

**D10 — Resume engagements omit `--model`; the session carries the model forward.** v1 seeds `record.model` from the first observed model id and passes it on every spawn; on resume that would pin the agent to the dispatch-time default and hard-fail if that id leaves the catalog. Platform resume semantics already carry the session's stored model forward when `--model` is omitted (the CLI default is deliberately not re-applied when an existing session is opened). First dispatch keeps v1 model behavior (validated request or harness default); every engagement after omits the flag — the agent continues as itself, same model, degrading gracefully.

**D11 — Send-initiated kills suppress the intermediate aborted delivery.** v1's kill path finalizes with delivery: an interrupt-and-redirect would deliver an "aborted" diagnostic to the parent and then the redirected engagement's real result — two deliveries for one logical redirect, the first misleading ("your agent died") immediately before it resurrects. When the kill originated from `subagents_send`, finalize with `deliver: false` (the completion entry still persists, satisfying per-engagement persistence). The suppression is attributed inside the shared kill helper — set only when that call actually initiates the kill of a still-running child — so an operator abort that races a send keeps its diagnostics, and a kill that lands on an already-exited child never relabels a finished engagement (whose real result then delivers normally). Operator aborts keep v1 delivery behavior unchanged — the parent should learn its agent died.

## Risks / Trade-offs

- **Double-writer hazard on a session file.** Structurally prevented at all three scopes: within a turn (sequential execution mode), within a process (synchronous claim, in-flight check over `child || run`, captured prompt, and a pre-spawn abort re-check), across restarts (pid probe over dispatch + engagement + completion entries). Each layer is small; all three are required for the spec's single-writer MUST to be true.
- **Shared session dir across pi instances (accepted).** The private session dir lives under the OS tmpdir and is deliberately not per-project, so sessions survive restarts; the registry itself stays session-scoped. One residual hazard: two pi processes restoring the *same parent session* can both restore the same agent record and engage it — no pid probe covers cross-instance writers of the same record (each probes only the other's child pid). This is pre-existing platform territory (two pi processes on one parent session are unsafe regardless); accepted for v2a, noted rather than engineered away.
- **Session-file growth and per-turn completion entries.** Each engagement embeds the full message log in a new session entry, amplifying v1's growth risk by the engagement count; restore folds latest-entry-wins so duplication does not accumulate in memory. Accepted for v2a; delta-encoding is a contained follow-up if it ever hurts.
- **Killed in-flight work is not in the session.** A turn aborted mid-stream contributes only what pi persisted before the kill (nothing if before the first assistant message); the corrective resume starts from the last coherent boundary, with a synthetic tool result where needed. Acceptable: the correction prompt itself carries the redirect, and D8 guarantees the precondition is explicit rather than silent.
- **Provider prompt cache warmth.** Each resume is a fresh process; a full-context model call is unavoidable. Within the provider's prompt-cache window the prefix is likely warm, making quick iterate loops cheap. No action; expectation-setting only.
- **Tmp dir growth and reclaim.** One session file per dispatched agent, never pruned by the extension. OS reclaim makes old agents un-re-engagable, but D8 converts that from silent amnesia to an explicit send failure — re-engagability is best-effort across long horizons, correctness is not at stake.
- **Cross-cwd invisibility.** An agent cannot be re-engaged from a different working directory (cwd-scoped lookup). Deliberate; the tool description documents it, and the miss fails explicitly (D8).
- **Stale-context / background-callback crashes.** Same exposure as v1 D6/D7 — all new background work (resume spawns, interrupt-then-resume chains) routes through the existing guarded dispatcher reading only `current`. Review checklist item, no new mechanism.
- **Non-TUI send is blocking-inline.** A slow resume child blocks the parent's tool call in `pi -p`/e2e, mirroring v1's blocking fallback. Consistent with v1's contract; not a regression.
